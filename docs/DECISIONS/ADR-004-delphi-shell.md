# ADR-004: Delphi shell with embedded React canvas

Date: 2026-10-29. Status: owner approved resolution; binding feasibility pending.

Native Delphi forms use design-time components with settings in the Object Inspector. Embedded React editor is the approved runtime UI exception. Prefer FMX Windows x64 with a tested WebView2 binding; document any fallback. Native code owns safe saves/dialogs/credentials/local processes. Versioned origin-checked bridge exposes allowlisted capabilities only to the trusted editor. Desktop delivery is required.

## WebView2 investigation, 2026-10-30

RAD Studio 37.0's installed `FMX.WebBrowser.Win.pas` uses WebView2 on Windows, but its WebMessageReceived callback returns without forwarding the message and its `ICoreWebView2` field is private. The public `FMX.WebBrowser.TWebBrowser` surface provides navigation and script evaluation, but does not expose a WebMessageReceived event or virtual-host mapping. Consequently, the stock control alone has not been shown to support the origin-checked native bridge needed here; using script evaluation as a substitute for an authenticated inbound channel would be unsafe.

A Windows-only FMX binding worth evaluating is [WebView4Delphi](https://github.com/salvadordf/WebView4Delphi): its upstream README states FMX support, its source exposes virtual-host mapping and web-message APIs, and its upstream license is MIT. It has not yet been pinned, installed, or compiled with this project's RAD Studio version. If adopted, retain its license and verify the WebView2 runtime/loader redistribution terms and version requirements. No dependency was installed during this investigation.

WebView2's [local-content guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/working-with-local-content) describes virtual-host mapping as a way to give packaged files a consistent web origin supporting storage APIs. Its [security guidance](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security) calls for validating message sources and contents. An implementation must map only the packaged editor directory, validate the actual sender URI on every inbound message, reject untrusted navigation/messages, avoid exposing raw filesystem paths or shell execution, and enforce explicit native capabilities. Browser permissions and local model startup must remain off until explicitly requested.

Next proof: pin and review a compatible binding, build a small IDE-editable FMX form on Win64, load packaged local assets using a virtual origin, exercise one harmless request/response and reject a message from another origin, then verify storage and navigation across restart. A successful proof does not itself complete the bridge, native saves, installer, or milestone M7.

## Initial request envelope

`src/desktop/bridge-protocol.ts` defines and tests an initial version-1 request envelope for the planned native boundary. It accepts only an explicit operation, request and session identifiers, and the current project identity; it contains no caller-selected path, shell command, or arbitrary payload. Validation checks the WebView event's actual sender URL against the reserved `https://webstudio.local` origin, checks the current session and project, and requires an independently granted capability. The validator is not connected to the editor or a native host, and cannot open or save files. The native implementation must independently enforce these checks, assign and revoke session/capability grants, constrain navigation, prevent replay where appropriate, and define bounded file transfer and response handling before implementing operations.

## Isolated Win64 feasibility proof

On 2026-10-30, upstream WebView4Delphi revision `0a27539f689026bf9d49e158d7078d249a2b4683` was cloned into a temporary evaluation directory. Its SimpleFMXBrowser example built with the installed RAD Studio 37.0 Win64 compiler. An isolated modification mapped a local test folder to `https://webstudio.local`, loaded its test HTML, and received `local-proof-ok` from the WebView event with source `https://webstudio.local/index.html`. The test application closed after the message. It did not load the WebStudio editor, access project data, or publish anything.

The binding's initialization code navigates to `DefaultURL` after `OnAfterCreated` returns. Setting the mapped URL as `DefaultURL` after establishing the mapping avoided the initial navigation overriding the test page. The upstream FMX example creates a native window parent at runtime even though the browser component itself is on the form; the project must respect the owner's IDE-editable form and runtime UI restrictions when deciding how to integrate it. This was an external feasibility test, not project UI code or a decision to add the dependency.

This proves only local asset mapping and a one-way message for one installed runtime. It does not establish origin rejection, message validation in Delphi, secure file operations, rendering of the editor, design-time installation, runtime redistribution, a clean-machine installation, or completion of M7. The exact dependency and WebView2 runtime requirements must be pinned and reviewed before integration.

## VCL design-time alternative, 2026-10-30

The pinned WebView4Delphi source has a VCL `TWVWindowParent` control with a published `Browser` property and an upstream SimpleBrowser example whose `.dfm` contains both `TWVWindowParent` and `TWVBrowser`. The example creates the native browser instance for that already-declared control after the WebView2 environment is ready. This is different from constructing the form's controls at runtime; the owner's restrictions still govern any proposed project implementation.

The unchanged upstream Delphi VCL SimpleBrowser example compiled successfully for Win64 Release with RAD Studio 37.0 MSBuild using the source search path from its project file. This was a compile-only test in the temporary evaluation directory: the example was not launched, installed into the IDE, added to this repository, or connected to WebStudio. It does not prove message-origin validation, offline editor loading, packaging, persistence, or clean-machine behavior. VCL is a candidate for further evaluation because the upstream FMX parent explicitly requires runtime construction; it is not yet an approved replacement for the FMX recommendation or a completed desktop shell.

## Isolated VCL local-editor proof, 2026-10-30

A separate, hidden Win64 proof used a `.dfm` declaring the VCL parent, browser and timer, with a private test WebView cache. It mapped the feature-enabled production `dist` folder to `https://webstudio.local` and received an injected test message from `https://webstudio.local/index.html` containing `WebStudio|107`, indicating that the root had rendered text. A later test established that this text was the app's 404 screen, not the editor dashboard. The process closed itself with exit code 0. It was compiled with RAD Studio 37.0 and the previously evaluated WebView4Delphi source; the proof files and cache are disposable test artifacts, not product code.

This narrowed the feasibility question: an IDE-declared VCL host could load a page from this build and receive a local-origin message on this machine. The proof checked one expected sender string; it did not test rejection of malicious origins, trusted navigation, native capabilities, safe file operations, UI editing in the IDE, licensing of a distributed runtime, installation, or release readiness. No shell architecture decision or dependency installation had been made at that point.

## Isolated VCL source-check proof, 2026-10-30

A separate hidden Win64 proof mapped two local test folders to `webstudio.local` and `untrusted.local`, navigated to each in turn, and sent the same test message. Its native event handler accepted the message whose WebView-reported source was `https://webstudio.local/index.html` and rejected the message from `https://untrusted.local/index.html`. It exited successfully with both results recorded. This exercised real WebView2 sender reporting and a simple native exact-source decision on this machine; the proof intentionally allowed navigation to the untrusted test origin so it could send the second message.

This is not a product bridge or complete security review. It does not test subframes, redirects, replay, malformed messages, capability grants, navigation prevention, file access, or a clean install. Any desktop implementation must independently enforce its origin and navigation policy and test those cases.

RAD Studio 37.0 also includes the VCL `TEdgeBrowser` control. In a separate hidden Win64 proof, that built-in control mapped the locally built app to `https://webstudio.local`, accepted a test message from that source, and rejected a test message from a second local virtual origin. The test exited successfully and used an isolated browser cache and a WebView2 loader DLL from the temporary evaluation; no third-party Delphi component was installed or added to the project.

This is a promising simpler candidate for the desktop host, but not a finished shell or security review. ## Native request validation increment

`desktop/bridge/WebStudio.Bridge.pas` now validates a small version-1 native request envelope against the actual sender URL supplied by its caller, a native session and project identity, and an explicit capability set. It rejects unknown fields and operations, invalid IDs, malformed or oversized messages and project-scoped requests without a project. The native validator accepts the canonical integer representation `1` for the version and requires the sender string to start with `https://webstudio.local/`; it is deliberately stricter than the TypeScript prototype's URL normalization.

The Win64 console smoke test `tests/native/DesktopBridgeValidationSmoke.dpr` compiled and passed with RAD Studio 37.0. The native session wrapper creates a 256-bit session ID with Windows' [system-preferred cryptographic random generator](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptgenrandom), accepts a host-provided project and grants, serializes validation and request-ID claims, rejects replay, and can revoke a session. It fails closed after 4,096 claims instead of forgetting old IDs. The test exercises distinct session IDs, concurrent duplicate requests, revocation and the request limit. The future host must deliver the ID only to the trusted editor, manage the session lifetime and avoid freeing it while requests are in flight.

This code is not connected to a WebView, does not choose or grant capabilities, restrict navigation or perform file operations, and is not a complete bridge or security sign-off. A future native host must pass the WebView event's source rather than trusting a message field, establish and revoke session grants, and test the entire boundary.

## Isolated WebView message event proof

## Blob-frame restriction

An isolated test first demonstrated that an HTML blob frame allowed by the earlier shell could invoke its parent's WebView message channel; the event identified the top-level page as the source. Origin and session checks alone therefore did not isolate that same-origin frame. The shell now cancels blob frame navigation, while retaining local `https://webstudio.local/` frame navigation. The Win64 bridge-event test confirmed the formerly successful blob-frame request did not reach its parent after the restriction; a separate isolated desktop test still imported and rendered the sample PDF using the current PDF.js canvas. The Win64 Delphi project built successfully.

Earlier descriptions of permitted blob frames in this decision record are historical. This change reduces one demonstrated risk; it does not prove all frame, script or content isolation. The production shell still disables web messages, and a future bridge must address trusted local frames, session delivery, navigations, redirects and untrusted content before enabling them. Older staged preview executables do not include this restriction.

The isolated native test also attempted to execute a `srcdoc` frame that invoked the parent channel; no request reached the handler during the test. This result applies to the tested WebView2 runtime and shell configuration, not all frame or navigation cases. A refreshed local test folder, `bin/DelphiWebStudio-Preview-20261030-2037`, contains the rebuilt shell and current editor assets; the prior preview is retained with a superseded notice. The folder remains an experimental preview rather than a release or clean-machine installation.

## Local-frame restriction

A follow-up isolated test loaded a synthetic HTML file from the mapped local origin. When the test page deliberately exposed a synthetic session ID to that same-origin frame, the frame could call its parent's WebView message channel and the event again reported the top-level page as its source. The shell now cancels all frame navigation, including local frames. The native test stages `tests/native/BridgeFrameTest.html` as `editor/frame.html`, repeats the demonstrated attempt, and observed no accepted request after the restriction. The shell and the test compiled for Win64; an isolated desktop test still imported and rendered the sample PDF with the canvas viewer.

This restriction also means embedded frame-based content, such as external video embeds, does not display inside the desktop editor. Website exports are separate and are not changed by this shell restriction. Earlier statements that local frames are permitted are historical. The production shell still disables web messages; these tests do not establish a complete bridge security boundary, and future support for frames needs a reviewed isolation design.

The isolated event test now sends a small JSON acknowledgement to the top-level page only after the native session accepts a request. The page received the matching request ID; duplicate, ungranted and revoked requests produced no acknowledgement. This demonstrates a minimal message round trip in the test harness, not a production response protocol, file transfer, session bootstrap, or permission prompt. The production shell continues to disable web messages.

## Desktop downloads

An isolated desktop test exposed a repeat-download failure: after one project save, WebView2 requested permission for multiple automatic downloads, and the earlier shell denied it while the editor reported an export. The shell now permits that request only for the local editor origin, only when the runtime supports making the permission nonpersistent. Other browser permissions remain denied. Each accepted local or local-blob download is deferred to the design-time Save dialog, which asks for a destination and has overwrite confirmation enabled; cancellation stops the download. Concurrent download dialogs are rejected. The website export message now says the download was requested rather than claiming it completed.

A Win64 isolated test using a separate WebView profile and test-only filenames exercised project save, website export, cancellation and another save. It verified the project and website ZIPs contain the original sample PDF and that cancellation created no file. The automated dialog test used a test-only show hook that selects the legacy Windows file dialog; the normal modern dialog, overwrite confirmation, clean-machine behavior and error handling still need interactive validation. This is a browser-download workflow, not the unfinished native project save bridge or an atomic-save guarantee. Earlier statements that all permissions are denied are historical.

The current local test folder `bin/DelphiWebStudio-Preview-20261030-2201` stages the rebuilt shell and editor with this dialog flow. It is an experimental preview, not an installer or release; the previous preview remains available with a superseded notice.

A separate isolated Win64 test closed the test shell after a download event queued its Save dialog but before that callback ran. It then executed the queued callback and completed without showing a dialog or creating the test file. This covers one shutdown ordering; it does not replace interactive modern-dialog or overwrite-confirmation testing.

## Desktop editor script policy

When the editor runs at `https://webstudio.local`, its trusted entry module installs a content security policy limiting subsequent scripts to the local origin, disallowing inline, data and blob scripts, restricting workers to the local origin or blobs, and disabling object embeds and base-URL changes. Browser development at other origins and exported websites are not given this policy. The policy is installed by the entry module after its initial imports, so it does not protect that initial boot or replace a trusted installation; it also does not block all network requests or establish complete XSS isolation.

An isolated Win64 WebView test verified the policy blocked synthetic inline, data, blob and external script attempts, then imported, rendered, searched and zoomed the sample PDF and exercised project save, website export, cancellation and another save. The saved and exported ZIPs retained the original PDF and the site viewer. The production shell still disables native web messages; session delivery, trusted installation, other content boundaries, modern-dialog interaction and clean-machine testing remain open.

The editor now describes project downloads as requested rather than completed. The desktop status line reports cancellation, and reports when the installed WebView2 Runtime cannot safely grant the nonpersistent repeated-download permission. An isolated legacy-dialog test verified that cancellation is reported and a subsequent save can still start; the normal modern dialog remains to be tested interactively.
