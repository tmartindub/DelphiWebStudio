# Local AI action foundation (experimental)

Last changed: 2026-10-30. This is a development-only foundation for M4, not a functioning AI wizard or model connection.

`src/ai/site-actions.ts` defines a versioned, preview-only request and a limited set of typed page, theme and block operations. Evaluation works on a copy of the validated project and returns a readable list of changes. It does not contact a model, execute commands, read files, publish a site or modify the editor. The result can be accepted only against the same source snapshot; a changed project or altered preview is rejected.

The editor's **Plan pages** command uses this contract for a manual workflow: choose blank About, News, Events and/or Contact pages, review their names and paths, then explicitly add them. Cancel leaves the project unchanged, and the accepted set is one undoable edit. Existing paths are unavailable, and a changed source project requires a fresh review. This is manual page planning, not AI generation; the tested local model is not connected to it.

The initial allowlist can create and rename pages, change six-digit theme colors, and add or edit limited hero and text blocks. It can move blocks and remove only supported hero or text blocks. It does not add media, run code, change URLs, publish or support arbitrary components. Rejected actions leave the input project unchanged. Unknown existing block fields are preserved.

There is no integrated local model, inference process management, model installer, model JSON-schema integration, conversational planner, or quality benchmark yet. The review dialog described below is not connected to a model host. The action contract and manual page planner do not complete M4 or provide a general security guarantee. Do not send private project data to an external provider without the user's separate opt-in.

## Isolated local inference feasibility test

On 2026-10-30, a temporary test on this PC (approximately 16 GB RAM, Intel Iris Xe graphics) used the official Windows x64 CPU build of [llama.cpp b12012](https://github.com/ggml-org/llama.cpp/releases/tag/b12012) and the [Qwen3-1.7B-GGUF model](https://huggingface.co/Qwen/Qwen3-1.7B-GGUF) at revision `90862c4b9d2787eaed51d12237eafdfe7c5f6077`. The runtime ZIP's SHA-256 matched the release's published `7605ee19d22ff58053d0df045f972367f6e6fd36bbcd02e7c0633ca639603a85`; the 1,834,426,016-byte Q8 model matched Hugging Face's published `061b54daade076b5d3362dac252678d17da8c68f07560be70818cace6590cb1a`. Upstream identifies llama.cpp as MIT-licensed and this model as Apache-2.0; runtime dependencies and distribution obligations still require a full review before packaging.

The model ran with the runtime's offline option on CPU. A temporary server bound to `127.0.0.1` on an ephemeral port, used a generated key file, disabled its web UI and slots endpoint, and rejected one unauthenticated `/v1/models` request. A fictional noncommercial community-site prompt returned a schema-constrained JSON object containing five page names and headlines: Welcome, About Us, Events, Resources and Contact. The temporary server was stopped after the test. A direct CLI attempt with a global JSON grammar reported an initialization error despite returning exit code zero; the structured server response succeeded. Consumers must check response content and errors, not process exit code alone.

This was a feasibility check, not an app feature or a quality benchmark. It did not generate an editable site, exercise the action validator or approval/undo flow, prove rejection of every unauthorized endpoint, establish process isolation, or verify installer and model distribution. The downloaded runtime and model were used only from a temporary evaluation folder and are not shipped with the project. A native lifecycle, protected credentials, timeouts, model acquisition/verification, structured request integration, safe user review, and broader quality testing remain necessary.

## Native process lifecycle increment

`desktop/ai/WebStudio.LocalAIProcess.pas` is an unconnected Win64 Delphi process component, not an installed AI feature. It starts a caller-selected `llama-server.exe` with a GGUF model and a key file, forces offline mode and loopback binding, disables the runtime web UI and slots endpoint, and avoids shell execution. It starts the child suspended, assigns it to a Windows job configured to kill owned processes when the job closes, and resumes it only after assignment. Stop targets that job, not unrelated applications. The component requires caller-supplied trusted SHA-256 values and compares them with the executable and model before starting. Checking a large model is synchronous and must be kept off the UI thread. These checks do not verify dependent DLLs or eliminate replacement races; the caller must establish a trusted, protected runtime installation and checksum source. The caller must also securely create and protect the random key file, select an available port, verify server identity/readiness and errors, and remove the key file. The component does not implement those responsibilities, inference requests, a user interface, an installer, or publishing.

On 2026-10-30, the Win64 Delphi compiler built `tests/native/LocalAIProcessSmoke.dpr`. With the temporary, checksum-verified runtime and model above, the smoke test checked invalid port, incorrect executable and model checksums, and duplicate-start rejection; it also checked process startup, local health, rejection of an unauthenticated model request, acceptance of the test key, and explicit shutdown. A separate intentional test-host termination confirmed its owned server's listening port closed. These tests do not establish complete endpoint security or replace the missing native host, review workflow and installer. No user project or site was sent to the model.

## Five-page plan conversion increment

`previewFivePagePlan` accepts an untrusted five-page name/headline plan and converts it into the existing action preview transaction. It requires a project with one empty Home page, creates distinct local page addresses, and rejects malformed or colliding plans. The first plan entry names Home; each page receives an editable Hero headline. A caller must show the generated changes and explicitly accept the unchanged preview; acceptance can be one undoable editor operation. Automated tests exercise acceptance and undo. The converter is available to the review dialog but is not yet connected to the local model and does not complete the AI wizard.

The editor now has a review dialog for a five-page plan delivered by a future native host. It displays each proposed page and headline before applying anything, rejects a response if the project changed during generation, and applies the approved plan as one undoable operation. An isolated browser check exercised a recorded model response, cancellation, approval, undo and a changed-project rejection. The native model host is not yet connected, so this dialog is not currently a way to generate a plan in the application.

A subsequent isolated inference run used the same locally evaluated runtime and model with a fictional community-site prompt. The resulting five-name/headline response is recorded as `tests/fixtures/local-ai-community-plan.json`. An automated test passed that response through the plan preview and acceptance, serialized and reopened the project, and verified the five exported HTML pages contain their headlines. The test used a temporary loopback server and key, then stopped the server and removed the key. This is one simple model response, not an end-to-end app feature or a model quality benchmark; native host integration, review UI and runtime/model packaging remain open.
